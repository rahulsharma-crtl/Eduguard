# Teacher-owned accounts

Teachers now select **Create account**, choose a pseudonymous username and their own password, save the one-time recovery code, then launch classrooms. Returning teachers sign in with the same account. Usernames are case-insensitive and limited to ASCII letters, digits, dots, underscores and hyphens; no email address is required. Registration is public, not an institutional identity check or a Google sign-in.

Passwords accept 6–128 characters and use salted Argon2id (19 MiB memory, two iterations, parallelism one). The app never persists plaintext passwords. Password hashing parameters follow the minimum Argon2id configuration in [OWASP Password Storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html). Password managers receive standard username/current-password/new-password autocomplete hints. The UI reminds teachers to choose their browser's Save password option in Google Password Manager or another manager. EduGuard cannot force that prompt or automatically save credentials into a Google account. It does not implement Google OAuth.

A cryptographically random recovery code is shown on registration and after reset only. Its SHA-256 digest is stored; the original is never recoverable from the database. Save it securely with the username. Anyone who obtains both can reset the account. Reset requires username, code and a new password. It atomically consumes/rotates the code, changes the password and revokes existing teacher account/room tokens. A teacher can then reopen owned retained rooms using a new sign-in. Losing both password and recovery code means no self-service recovery; no email/reset link or support bypass is implemented.

Teacher accounts own their new rooms. Account credentials cannot be used as room tokens, room credentials cannot create more rooms, and teachers cannot reopen other teachers' rooms. Account/room tokens expire after 12 hours. Account tokens persist in sessionStorage only; passwords and recovery codes are not written to browser storage. Clearing browser data loses sign-in state, not the database account. Sign out clears this browser's account credential; it is not global token revocation. Reset revokes all of that account's teacher tokens. Existing student invitation, consent, media and telemetry contracts remain unchanged.

## Deploy

1. Deploy the updated API and frontend together. New teacher routes are `/teachers/register`, `/teachers/login`, `/teachers/recover`, `/teachers/rooms` and `/rooms/{id}/teacher-resume`.
2. Keep a stable private **AUTH_SIGNING_KEY** (at least 32 characters), **DATABASE_URL** pointing to persistent PostgreSQL, **ALLOWED_ORIGINS**, and **SIGNALING_URL**. No teacher password environment variable is required for startup.
3. Remove **TEACHER_ADMIN_PASSWORD** from Render to disable the optional legacy room-creation path. If a valid non-default legacy secret remains, old clients can still create unowned rooms with it. Empty, short and `admin123` values disable that path without blocking startup. New frontend uses accounts only.
4. Back up the database and run `python -m scripts.migrate_db` once before rollout. Additive migration version 3 adds teacher accounts and nullable room owner IDs/indexes. Existing room/history records are preserved. Old unowned rooms remain accessible through their existing valid capabilities; new teachers cannot claim them by knowing their ID. Migration concurrency and PostgreSQL verification limitations from VALIDATION_REPORT.md still apply.
5. Use a fresh/private window after deployment to create a test account and verify registration, sign-in, reset, room ownership, broadcast and reports. Do not put passwords in Vercel `VITE_*` settings.

Teacher credentials persist beyond the seven-day classroom retention window. Classroom deletion leaves the account intact. Account removal is currently an operator workflow; there is no self-service account deletion UI. Backups, retention and administrative access to credentials need deployment policies. Public signup has bounded in-process IP/username throttling, not distributed abuse prevention, email verification or MFA. Keep signup behind appropriate organizational access controls if public registration is not desired; the UI does not verify employment as a teacher. Stateless account sessions need HTTPS and XSS protections; no production-readiness claim is made by this feature.

## Validation

See the updated tests in `tests/test_teacher_accounts.py` and `tests/browser/session.test.mjs`. Unit/API coverage includes hashing and unique salts, duplicate usernames, generic failed login, password policy, account persistence after restart, expired tokens, throttling, room ownership, recovery rotation and invalidation of old access. Browser coverage uses the actual React/FastAPI flow for registration, recovery-code acknowledgement, sign-out, failed login, password reset, new login and a classroom lifecycle. Standard autocomplete attributes are tested; the real Google Password Manager prompt cannot be forced or established by headless testing.
